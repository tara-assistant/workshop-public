# Trip Planner: working rules

- `.agents/skills/trip-planner/` is the one canonical, portable Agent Skill package. It contains `SKILL.md` and optional `references/`; keep the folder name aligned with the frontmatter `name`. Keep exactly two intentional trip samples in `samples/`: `sardegna.json` is the built-in preset; `portugal-6-day-demo.json` is a date-labeled illustrative sample, not a preset or confirmed plan. Do not add other bundled itineraries. Keep generated trials in ignored `tests/local/skill-trials/`.
- Maintainer-only scratch work lives in ignored `tests/local/`. That folder is not included in a public checkout or deployment and is never pushed. Layout:
  - `tests/local/scripts/` test, probe and server scripts (`_serve.py` on port 8766, `_flow.py`, `_shot.py`, `_verify.py`, `_verify_sardegna_photos.py`). Run them from `tools/trip-planner`, for example `python tests/local/scripts/_flow.py`.
  - `tests/local/patches/` one-off patch scripts. Keep each one after running it so it can be referenced later. Never delete a patch script.
  - `tests/local/evidence/` screenshots, reports, research notes and result logs. Keep unique evidence; mockup screenshots and their check report belong together in `tests/local/evidence/mockups/`.
  - `tests/local/skill-trials/` generated itinerary trials and preserved non-release examples.
  - `tests/local/README.md` repeats this layout.
- The live browser preserves its active trip and settings in localStorage. Do not clear or reset that profile for tests; use isolated Playwright contexts for the bundled Sardegna sample.
- The Trip Planner review mockup at `tests/local/evidence/mockups/trip-planner-review-20261015.html` fetches the canonical `samples/sardegna.json`. Open it over HTTP through `python tests/local/scripts/_serve.py` at `http://127.0.0.1:8766/tests/local/evidence/mockups/trip-planner-review-20261015.html`, not as `file://`. Its Playwright checker starts a temporary server and writes viewport screenshots and its report beside the mockup.
- For a production-app preview, run the tracked `serve.mjs` from `tools/trip-planner/`, not the `workshop/public/` root; it binds only to `127.0.0.1` and honors `PORT` for alternate ports. Use a disposable browser context, never the saved-trip profiles on ports 8766 or 8767.
- Only production code and explicitly approved documentation are published. Plans, tests, and working notes stay local unless explicitly approved for public release. The project `.gitignore` excludes them by default; ignore rules do not affect files already tracked by Git.
- Repository unit tests sit beside the code they test, such as `schema/validate.test.mjs` and `js/*.test.mjs`. They are tracked and run by CI. Keep browser harness scripts, screenshots, reports and generated trials under ignored `tests/local/`; do not add that local output to a release.
- Do not leave scripts, screenshots or trial output at the `tools/trip-planner` root.
- Scratch build folders named `dist-*` at the repository root are local and ignored. Only `dist/` is produced by the real Pages build, and it is ignored too.
- The app has no API keys and no Mapbox code. Do not add either.
- The app has no agent connector or MCP server. Agents follow the canonical skill and hand the app a trip file.
- Use the latest operator directions below to refine the approved 2026-10-21 layout concept in `tests/local/evidence/mockups/my-trip-planner-layout-concept-20261021.html` as the production visual source of truth. Keep the centered overview, floating day cards, quiet map, and equal desktop panels. Base headings remain collapsible and light; each base has one distinctly hued, clearly visible but still soft back panel confined to its header row and Add day control, with a slim color accent edge; expanded day cards stay neutral. Avoid nested wrapper backgrounds or shadows.
- Do not place `Add stop` at the bottom of a base or itinerary. Put it in the relevant day card header. Keep `Add day` beside its base heading, and keep `Add a base` available in the trip menu.
- Balance the desktop itinerary and map instead of letting the map dominate the workspace. Keep base names readable at desktop and mobile sizes. On mobile use one fixed-size map, with no expand/collapse or resize control; selecting a stop must not change its size.
- Explain settings in context. Use a left navigation rail with a matching explanation pane on wide screens, and compact, reachable tabs on narrow screens. Editing is always available on days and stops; keep it separate from visited and packing ticks, with no Edit mode switch.
- Offer illustrated Standard and Satellite map styles; do not add a Topo layer or the removed inline map-help sentence. Keep required map attribution visible beside the map. OpenFreeMap's own name is optional under its current terms and may be hidden from the map control; retain © OpenMapTiles and OpenStreetMap credit, with OpenFreeMap still listed in Settings > Services. Show hiking tracks and elevation only when supported by GPX or verified data.
- Keep the footer removed. Put the exact copyright line “© 2026 MetaEngineers Hub.” in Settings > About, with MetaEngineers Hub linked to this project’s repository. Put detailed provider credits in Settings > Services, while required map attribution stays beside the map. Beside each day photo, show the author, linked licence and linked Commons source page.
- Use official `thumb.wikimedia.org` imageinfo thumbnails for Wikimedia sample photos rather than `Special:FilePath` redirects; the redirects returned `ERR_BLOCKED_BY_ORB` in the browser and removed photos from preview. Keep photo author, licence and Commons source credits intact.
- Automatic photo lookup runs only for a newly added stop; it does not backfill existing imported/sample trips. Curated sample day photos must be added to the sample JSON with full imageinfo thumbnail, author, licence and source metadata before release.
- Place each stop's forecast and any hiking or GPX detail inside the relevant stop or day, not in a separate map-side card. Fetch weather automatically only for expanded days in visible, expanded bases and show it under each located stop inside the open day. Collapsed days must not request new weather or show a weather summary. Show only a condition icon and a low-to-high temperature range; distinguish forecast from historical typical data accessibly (and in a concise tooltip). Do not show rain, wind, provider, freshness, explanatory weather paragraphs or duplicate weather cards. Keep automatic date-based fetching. Keep the full day date visible and put the packing checklist after the day content at the bottom of its card. Do not describe a periodic forecast as real-time weather.
- Keep the desktop itinerary on the left and map on the right, equal in height. The itinerary scrolls inside its panel; on mobile the full page scrolls. Put trip progress above both desktop panels and above the map on mobile.
- Keep Menu visible above itinerary days on mobile, with Settings in its App section even when no trip is loaded, use explicit trip-stat labels without unexplained dots, and explain Standard and Satellite beside the map controls. Do not put provider credits in the footer.
- Use restrained transitions and respect reduced-motion preferences.
- In each expanded day, show visited checkboxes on the left beside a thin vertical stop timeline, retain compact stop-type icons, and put clickable navigation and website actions beneath the stop details. Remove the six-dot drag handle; keep reordering through the explicit Move up/down controls.
- Group short day tips, booking, food and packing details at the bottom in compact, restrained styling, with no oversized cards or repeated decorative icons. Retain stop/category icons at the top. Base header rows, including Add day, have subtle contrasting color-tinted back panels with quiet borders and readable text; expanding a base never extends that tint behind day cards, which remain neutral individual surfaces. Outer map and itinerary wrappers stay transparent.
- On desktop, show the itinerary directly in the left column and the map in the right column. Remove both outer backing panels, preserving the individual day cards and the map itself.

- Overview, itinerary and map share one centered content-width boundary; panels must not extend beyond it. Leave comfortable bottom page spacing after the last panel/card.
- Give each base a distinct, stable soft tint confined to its header row and Add day control; do not extend the panel as the base expands or randomize colours on render. Keep base text readable against the tint. Use crisp, small inline SVG chevrons for expanded/collapsed state. Keep the UI modern, lively, elegant and uncluttered.
- Remove Add GPX track and Replace GPX controls. Preserve imported track data, display and export support.
- In the canonical portable skill, stop descriptions address the traveller naturally and warmly. Keep OSM/OpenStreetMap, search/geocoder/mapping verification methods and provenance in source/links metadata, not traveller-facing descriptions. State material uncertainty briefly with a useful next action. Skill edits must not rewrite saved trips or the shipped Sardegna sample.


- Real trips and drafts require traveller-confirmed startDate/endDate and a date for every day. Ask for missing dates and wait. Only when explicitly asked for an illustrative demo may you use example dates: agree them with the requester or clearly disclose the chosen dates, include all root and day dates, and mark both title and note as "Illustrative demo; not a confirmed travel plan". This exception never applies to an ordinary trip request; never substitute research dates. The New Trip first-date field is required. The bundled Sardegna sample already has dates and must not be changed for this refinement.
- Suppress only the obsolete no-travel-date research diagnostic pattern in day-tip rendering: "No travel dates: weather values and forecasts are omitted. Research check date: YYYY-MM-DD, not the travel date." Keep stored trip data intact and do not generate this tip in the canonical skill.
- Packing checklist items occupy individual full-width rows at the bottom of each expanded day, after compact booking, food and tips. Keep hints restrained and stop descriptions warm and natural, with top-level stop icons retained. Packing rows have no horizontal divider lines.
- Keep meaningful icons inline to the left of their labels and vertically aligned, including stop titles, category chips and action controls; map-style thumbnails are illustrations and may remain above their labels. Put Edit, Move up, Move down and Delete in one expandable Actions control, retaining disabled boundary moves.

- Keep one header control: `#menuBtn` opens `#tripMenuDlg` titled Menu, with This trip and App sections. Keep `#libraryBtn` and `#settingsBtn` (inside App). Menu and Settings share one responsive visual language: branded header, left rail/compact mobile tabs, scrollable content, fixed footer, inline icons beside English labels, and consistent action rows. Keep every This trip destination inside the Menu as a subpage with back navigation, including My trips and its new/import/restore controls, Share and export, Add a base, Manage bases, and Clear ticks; do not open separate dialogs for these flows. Close Menu before opening the separate Settings dialog, reset Settings to Agent skill on every opening, and return focus to the Menu App section when navigating back. Settings sections are Agent skill, Services and About; weather stays automatic inside expanded days, with provider endpoints under Services.
- Keep the canonical skill portable: no app implementation/layout instructions, source provenance only in metadata, JSON import steps, and GPX described as a separate imported trip rather than a stop attachment. The Portugal sample is shipped separately from the skill package; its title and note must both say exactly “Illustrative demo; not a confirmed travel plan”, with explicit root and day dates. General real trips still require traveller-confirmed dates.
- A fresh browser profile starts with an empty trip library: never auto-load a bundled sample. The empty state offers the Sardegna and Portugal demos, a manual trip and an import path. Agent use is skill-and-file handoff only; do not imply direct connection to or control of the app.
